### Colab 后端配置与验证范围

GPTQModel 7.6.0 的加载子池 `model_loader:cpu` 固定需要 2 个 worker，CPU 父池由
`GPTQMODEL_CPU_WORKERS` 控制。Notebook 在后端初始化前将父池设为至少 2，保留更大的显式配置；

AWQ 使用 `awq_torch` 打包、`awq_gemm_triton` 重载推理。两者声明同一 GEMM 格式，
但 [Torch 类](https://github.com/ModelCloud/GPTQModel/blob/v7.6.0/gptqmodel/nn_modules/qlinear/torch_awq.py)提供原始权重 `pack`，
[Triton 类](https://github.com/ModelCloud/GPTQModel/blob/v7.6.0/gptqmodel/nn_modules/qlinear/gemm_awq_triton.py)没有该接口。
[后端选择器](https://github.com/ModelCloud/GPTQModel/blob/v7.6.0/gptqmodel/utils/importer.py)分别检查打包和推理能力。

对形状 `(32,128)`、组大小 32/64/128 的权重，隔离执行官方 pack 方法的 CPU 检查表明：
Torch 与 GEMM 的 `qweight/qzeros/scales/bias` 一致，解码值也与独立构造的已量化权重一致。
这只验证布局，未验证完整模型校准、Triton 编译或 GPU 性能；具体源码哈希见既有[实现核验清单](../references/provenance/implementation_checks.json)。

当前协议 v4 默认分开测 prefill/decode，记录每次计时，并核对实际生成 token 数。
探针准备与生成预热可能包含编译，不应把它们称为纯编译时间。内容、格式、EOS 和长度上限分别报告。
原始 ZIP 检查器接受明确标注的部分失败，核对文件清单、哈希、执行代码及成功/失败集合；还会拒绝非有限数、非法 token 数和重复 JSON 字段，并以逐次计时、NLL 与计分数核对已提供的中位数、吞吐和 PPL。启用分阶段测量时，也会检查 prefill/decode 的重复次数和派生指标。
这些检查证明包内结构与数值关系一致，不证明数据真实性、任务质量或 kernel 确实执行。修改 prompt 或协议后，要在同一轮重新建立 FP16 基线。

当前 Notebook 对已应用 chat template 的文本显式设置 `add_special_tokens=False`，避免分词阶段重复添加控制符。结果写入发生在方法评测完成之后；文件系统错误会停止运行，不会把已完成配置同时登记为成功和算法失败。部分文件写入失败时，应将该目录视为未完整发布，不用旧哈希清单解释新文件。

`prefill_forward_seconds_median` 对应的实际区间包含一次模型前向、首 token 的 argmax、局部对象释放与同步；`decode_seconds_median` 包含缓存追加、mask 构造、后续前向与 argmax。它们是本 Notebook 的阶段墙钟时间，不是纯 GEMM/Attention 内核时间，也不包含客户端网络与服务排队，因此不直接等同于服务 TTFT/TPOT。

## 10.2 先做三个修改，培养直觉

1. 对照第 04 个实验新增的 `X_identity = I / sqrt(2)` 分支：它仍通过 `H_identity = 2 * X_identity.T @ X_identity` 得到单位 Hessian。RTN 和补偿均为 `[1,1]`，损失均为 0.16。不能只替换 `H` 而保留原 `X`，否则输出损失与二次型不再一致；原例子的断言也不适用于新例子。
2. 复制 [AWQ](03_离群值与缩放.md#awq) 或 [SmoothQuant](03_离群值与缩放.md#smoothquant) 小节内的代码，把 $X[:,0]$ 的放大因子从 20 改成 1，观察相对收益。原例也可用 `--technique awq` 或 `--technique smoothquant` 单独运行。
3. 复制[分组量化](01_均匀量化与误差.md#grouping)小节内的代码，把位宽从 4 提高到 8，再把组大小减半。比较误差和 `bits/weight`。保持基础实验中的 INT4 手算和打包断言不变，避免将实验参数变化与回归检查混在一起。

修改代码后保留一份原始结果，避免把新的实验误认为教程初始记录。

## 10.3 真实模型的评估顺序

第一步，固定浮点基线：模型 revision、tokenizer、prompt/chat template、上下文配置和解码参数保持一致。

第二步，分离校准集与评估集。校准数据用于选量化参数，评估数据用于检验泛化；反复用测试集挑配置会使结论偏乐观。

第三步，先量权重、层输出误差，再看任务。层输出误差可以快速定位坏层，但不能替代模型级质量。

第四步，确认真实 kernel 已启用，再测内存和速度。若只是保存更小、运行时全部展开成 FP16，实际峰值显存和延迟会与预期不同。

第五步，检查实际使用场景：语言、代码、数学、长上下文、工具调用、结构化输出。只用一份短文本 perplexity 很容易漏掉退化。

## 10.4 Perplexity 是什么，为什么不够

对一段 token 序列，平均负对数似然：

$$
\operatorname{NLL}=-\frac1N\sum_{t=1}^N\log p(x_t\mid x_{<t}).
$$

困惑度：

$$
\operatorname{PPL}=e^{\operatorname{NLL}}.
$$

PPL 由 5.0 增到 5.2，表示平均概率建模有退化；不意味着“准确率下降 4%”。它与问答得分不是线性对应关系。

比较 PPL 时，还必须固定 tokenizer、文本切分、滑窗步长、上下文长度、BOS/EOS 和掩码规则。不同 tokenization 下的 PPL 通常不能直接横向比较。

对于推理任务，还要看最终答案正确率、不同随机种子、长度分布与重复/格式错误。量化可能只改变早期少量 token，却影响后续整条生成轨迹。

## 10.5 性能要分别测什么

| 指标 | 意义 | 常见误读 |
|---|---|---|
| 模型文件大小 | 磁盘存储 | 不等于运行峰值显存 |
| 峰值显存 | 权重、KV、工作区等总需求 | 只报权重大小会低估 |
| TTFT | 请求到第一个 token 的时间 | 与 decode 吞吐是不同阶段 |
| TPOT / ITL | 输出 token 的间隔 | 均值可能掩盖尾延迟 |
| tokens/s | 单请求或系统总吞吐 | 必须说明并发数与统计方式 |
| prefill latency | 处理 prompt 的耗时 | 不代表长序列 decode 表现 |
| 离线量化成本 | 生成量化模型花费的时间、内存 | 不属于单次推理成本，但影响迭代 |

GPU 测时要正确同步或使用设备事件；先预热，避免将初始化/编译与稳定运行混在一起。固定输入输出长度，否则“生成更快”可能只是模型更早结束。

## 10.7 哪些方法可以组合

有些方法改变的是不同部分，因此可以组合：

- 缩放/旋转预处理 + GPTQ 权重量化；
- 权重量化 + 独立 KV cache 量化；
- 低比特主体 + 少量高精度例外；
- 量化基础模型 + LoRA 微调；
- 合法等价变换 + 支持该分布的低精度硬件格式。

但“可组合”不是无条件开关：如果两个方法各自改变权重布局、量化网格或 Attention kernel，直接叠加可能失效。需要把完整计算图与数据布局对齐。

## 10.8 为什么本教程没有跨论文的总排行榜

论文可能使用不同模型版本、不同分组、不同校准预算、不同保留层、不同微调数据，甚至一个报告 kernel 时间，另一个报告完整生成。

公平比较至少要求：同模型、同评估协议、相近有效位宽、明确量化/微调预算、同目标硬件、同 workload。缺少这些条件，比较“某方法 5.6 PPL，另一方法 5.7 PPL”很容易误导。

本教程提供可复算的数学、适用条件和原始来源。实际选型最终应在你的模型和硬件上验证。

## 10.9 读新论文时用这七个问题

1. 量化的是 W、A、KV，还是算子中间结果？
2. 表示是标量整数、浮点、向量码本，还是带稀疏例外？
3. 每多少个元素共享尺度？完整平均位宽是多少？
4. 使用权重误差、输出重建、任务损失还是蒸馏目标？
5. 优化了权重、尺度、舍入、旋转、码本中的哪些变量？
6. 推理额外需要哪些操作？有没有对应硬件实现？
7. 结论来自哪些模型、任务与计算预算？有何失效案例？

能回答这七个问题，就能把新方法放回前面几章的数学框架中。

## 10.11 按技术缺口与证据强度确定研究优先级

技术覆盖应同时看对象、优化变量、损失、表示和执行方式。93 项带图示示例是教学索引，不是独立算法数，也不穷尽全部论文。
补充专题采用机制与原文对照，不把未实现的论文计算成新增可执行复现。

| 研究维度 | 需要同时比较的路线 | 实验优先级 |
|---|---|---|
| 无数据与有数据校准 | RTN/HQQ、SINQ/DualQuant、AWQ/GPTQ | 相同最终格式、独立目标任务与完整校准成本 |
| 超低比特优化 | 固定网格、LeanQuant、GPTVQ/AQLM、PV-Tuning、三值转换 | 同总位宽、码本/平面开销和适配预算 |
| 长上下文存储 | K/V、MLA 潜变量、循环状态 | 先固定架构，再比较精度与生命周期策略 |
| 系统执行 | INT GEMM、浮点反量化、位平面 LUT、专用移位单元 | 计真实算子、访存与端到端时间 |
| 质量保真 | PPL、教师分布、知识/代码/工具任务、长轨迹 | 每类任务独立底线与配对统计 |

[统一量化评估 v3](https://arxiv.org/html/2507.17417v3)有助于将预处理变换与量化误差缓解拆开做消融；
但某实验中组合收益可加，不构成任意方法可以直接叠加的定理。建议使用小型因子实验：无/有变换 × RTN/补偿，
再在相同总预算下加入码本、适配器或高精度保留，避免同时改变太多条件。

### 与推测解码的组合不能把两个加速比相乘

[Speculative Decoding Meets Quantization v2，§3](https://arxiv.org/html/2505.22179v2)讨论量化如何改变 draft、验证和逐 token 解码的相对成本。
若一次 speculative 周期平均接受 $a$ 个 token，耗时为 $t_d+t_v$，相对逐 token 成本 $t_0$ 的收益约为
$a t_0/(t_d+t_v)$。量化已经降低 $t_0$ 后，草稿开销占比反而可能升高；最佳草稿长度需重新测量。

“精确推测解码”保持的是其验证目标模型的分布。若目标模型已经量化，这一保证指量化目标，
不会恢复原始 FP16 模型的输出分布。应分别报告接受长度、draft/verification 时间、目标模型质量与吞吐。

### 近期预印本如何影响判断

对首次发布仅数日的 RoleQ、DualQuant、QuantMLA、循环状态与 MoE 分配工作，先采用可核对的机制与限定实验结论，
不将其单篇最优结果写成普适排行榜。没有独立复现时，优先用作消融假设和覆盖检查；
还应保留负面结果、校准分布变化和低频任务退化，而不是只收集最高分。

“固定权重格式下的校准泛化”已填写一组 [GPTQ/AWQ/LeanQuant/DRQ 证据对照](科研进阶_高质量量化论文路线与清单.md#calibration-evidence-comparison)，列出模型、位宽、校准预算、原文结果和失败边界，作为从技术索引进入具体选题的示例。

## 10.12 校准数据协议：从文本到实际参与统计的 token

<a id="calibration-protocol"></a>

“用了 128 条校准数据”不是完整配置。同样的条数，序列长度、语言、模板、截断位置与生成阶段不同，产生的激活统计也不同。数据准备与训练数据组织的背景可参考[《大语言模型》§4.2、§7.2](https://llmbook-zh.github.io/LLMBook.pdf)。用于量化时，至少固定下面的处理链：

1. **确定目标输入分布**：自然文本、中文对话、代码、长推理或混合任务；显式选择各域比例，保留独立验证与测试数据。
2. **确定预处理**：固定 tokenizer/revision、chat template、特殊 token、截断方向、文档边界以及样本拼接规则。模板已添加特殊 token 后，后续分词不能再次无意添加同一 BOS/EOS。
3. **统计实际有效 token**：同时报告序列条数、有效 token 总数、长度分布及各域占比。长样本通常贡献更多 token，不能只比较条数。
4. **采集目标模块输入**：处理 padding 掩码、形状和模块顺序；声明统计来自浮点模型，还是已量化前层所产生的输入。
5. **观察稳定性**：改变样本量或独立采样种子，对照尺度、裁剪率、二阶统计、独立验证集质量与校准成本。

### padding 掩码与加权方式会改变目标

设第 $i$ 条序列的有效长度为 $T_i$，输入行向量为 $x_{it}$。等 token 权重的二阶矩是

$$
C_{token}=\frac{\sum_i\sum_{t=1}^{T_i}x_{it}^Tx_{it}}{\sum_iT_i},
$$

等序列权重则是

$$
C_{sequence}=\frac1N\sum_i\frac1{T_i}\sum_{t=1}^{T_i}x_{it}^Tx_{it}.
$$

两者估计不同的分布，均不等于“先 padding 再对所有位置平均”。`attention_mask` 传进模型不代表校准 hook 已自动过滤 padding 位置；padding 的隐藏状态也未必为零。应在正确的张量轴上应用有效位置掩码。

<!-- depth-example: calibration_weighting -->
```python
import numpy as np
X = np.array([[[1.], [0.], [0.]], [[3.], [3.], [3.]]])
mask = np.array([[True, False, False], [True, True, True]])
valid = X[mask]
C_token = valid.T@valid/len(valid)
flat = X.reshape(-1, 1)
C_unmasked = flat.T@flat/len(flat)
C_sequence = sum((row[m].T@row[m])/m.sum() for row, m in zip(X, mask))/len(X)
assert np.isclose(C_token.item(), 7.)
assert np.isclose(C_unmasked.item(), 14/3)
assert np.isclose(C_sequence.item(), 5.)
print('token / unmasked / sequence:', C_token.item(), C_unmasked.item(), C_sequence.item())
```

本例将 padding 值设为零仍得到不同统计；真实 padding 激活非零时还可能改变方向。若某算法不除样本量且 damping 也同比缩放，部分全局常数可能抵消，但不能据此忽略一般的掩码和样本加权问题。

### 顺序校准与缓存生命周期

对逐层或逐块方法，应显式区分：浮点输入对浮点输出、量化前层输入对浮点目标、以及学生自身轨迹上的目标。更换一种输入协议后，得到的改善不能全部归因于量化优化器。临时 hook 应在使用后移除，缓存张量应按预算释放，避免一次校准意外保存全部层的激活。

KV 校准还需覆盖目标位置、上下文长度和 prefill/decode 阶段。静态校准范围、在线动态范围与残留窗口是不同机制；“无需离线数据”不等于不依赖实际输入分布。调参使用验证集，最终结果使用隔离测试集；不能不断根据测试 PPL 修改校准数据。

## 10.13 质量差异要有统计单位和任务边界

<a id="evaluation-statistics"></a>

**先正确聚合，再讨论差异。** 对多个文本窗口，保存实际参与预测的 token 数 $n_i$ 与 NLL 总和 $s_i$，总体 PPL 为
$\exp(\sum_i s_i/\sum_i n_i)$。不应对各窗口 PPL 直接算术平均，也不应忽略因 shift、padding 或重叠掩码而减少的计分 token。不同 tokenizer 的 token PPL 仍不可直接相比。

任务准确率应固定答案解析、拒答、格式错误、超长截断和失败请求的计分规则。同一题比较浮点与量化结果时，应做配对差异分析。bootstrap 可按题目、文档或会话重采样，并保持同一样本的模型配对；不能把一段文档内高度相关的 token 全当成独立样本。置信区间描述采样不确定性，不能修复测试污染、错误标签或偏置的自动裁判。

“下降 0.2 分”是否有意义，取决于题目数、差异分布与随机解码重复。固定随机种子有助复现，但两个模型在概率或调用路径不同后，同种子不保证产生相同随机轨迹。确定性固定前缀 logits/PPL 和自由生成质量应分别报告。

| 使用场景 | 除 PPL 外至少观察什么 | 公平对照条件 |
|---|---|---|
| 普通对话与指令 | 内容正确、模板遵循、EOS 与长度截断 | 同 prompt、模板、解码策略 |
| 代码、数学与工具 | 执行/最终答案、参数与结构正确性、重试次数 | 同测试、工具返回与预算 |
| RAG | 检索召回、给定证据下回答、引用是否支持结论 | 固定检索结果后测生成量化，再测全链路 |
| 长上下文 | 位置与长度分桶、信息提取、跨段任务、长轨迹稳定性 | 同有效上下文和位置编码设置 |
| 多模态模型 | 文本与图像/音频条件下分别评估、分组件消融 | 固定模态预处理与输入；注明只量化 LLM 还是还量化连接器/编码器 |

RAG 与多模态在 [Hands-On Large Language Models 第 8–9 章配套材料](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models)中是独立任务流程；这里强调评测分解，不声称文本校准足以覆盖其他模态。综合指标框架可对照[《大语言模型》第 12 章](https://llmbook-zh.github.io/LLMBook.pdf)。

## 10.14 服务评测：单请求变快与系统承载更多请求

<a id="serving-evaluation"></a>

量化可能通过缩小权重或 KV 让系统容纳更多并发，但随之增加的排队、batch 和内存读写会改变延迟。应同时做两类对照：**固定负载看延迟与资源变化；固定延迟目标看最大可承载负载**。服务背景见 [AI Systems Performance Engineering 第 16 章配套材料](https://github.com/cfregly/ai-performance-engineering/tree/main/code/ch16)与 [vLLM 官方服务基准实现](https://github.com/vllm-project/vllm/blob/main/vllm/benchmarks/serve.py)。

### 从时间戳定义指标

对请求 $i$，令 $a_i$ 为客户端发出时间，$f_i$ 为收到首个输出 token 的时间，$e_i$ 为收到最后一个输出 token 的时间，输出数量为 $n_i$，则

$$
TTFT_i=f_i-a_i,\qquad E2E_i=e_i-a_i,\qquad
TPOT_i=\frac{e_i-f_i}{n_i-1}\quad(n_i>1).
$$

ITL 是逐相邻 token 的实际间隔，TPOT 是该请求的平均间隔。单 token 输出没有可观测的后续间隔，应单列处理；客户端可能按多个 token 一个 chunk 收到数据，也不能把 chunk 间隔直接称为逐 token ITL。

固定观测窗口为 $T_{wall}$ 时，总输出吞吐是 $\sum_i n_i/T_{wall}$，其中 $n_i$ 必须只计入该窗口内收到的 token，而非窗口外的完整请求输出。它并非把各请求的 tokens/s 相加。请求级均值和 token 级加权均值也应区分。

令延迟目标分别为 $\tau_f,\tau_p$，定义在所选窗口完成且满足这些目标的请求数为 $N_{good}$，则请求 goodput 为

$$
G_{latency}=N_{good}/T_{wall}.
$$

它仅表示延迟达标吞吐。任务答案质量还需单独门槛，不能把延迟达标视为回答正确；第 16 章的成功任务成本进一步考虑质量。

<!-- depth-example: serving_goodput -->
```python
import numpy as np
arrival = np.array([0., 0.])
first = np.array([.1, .3]); last = np.array([.3, .9])
tokens = np.array([3, 4]); observation = 2.
ttft = first-arrival
tpot = (last-first)/(tokens-1)
good = (ttft <= .2) & (tpot <= .15)
assert np.allclose(tpot, [.1, .2]) and np.array_equal(good, [True, False])
assert len(tokens)/observation == 1.
assert good.sum()/observation == .5
assert tokens.sum()/observation == 3.5
print('requests/s, latency-good requests/s, output tokens/s:',
      len(tokens)/observation, good.sum()/observation, tokens.sum()/observation)
```

这是时间戳的算术示例，没有启动模型服务。观测窗口是否包含预热、开始前已存在的请求、结束后的排空阶段，都要预先定义。

### 负载与失败必须进入结果

- **固定并发的闭环负载**：请求完成后再发新请求；系统越慢，实际到达率越低。它适合测该并发下表现，却可能掩盖真实突发排队。
- **按到达率发送的开环负载**：按预定时间发请求，记录实际发送时刻、队列增长与拒绝；限并发后实际发送率可能低于目标，二者都应报告。
- **混合长度与缓存状态**：分别覆盖短/长输入、短/长输出、冷/热前缀缓存；相同并发数不等于相同有效工作量。
- **失败和尾延迟**：报告成功、拒绝、OOM、超时和部分输出，以及 p50/p95/p99。不能删除慢请求后仅对成功样本报告“整体”延迟。

先用固定输出 token 数定位系统吞吐，再用自然 EOS 的真实任务测体验与成本。调度器、连续批处理、chunked prefill、前缀缓存和量化配置分别做消融，否则无法确定收益来自哪一项。

### 10-03｜PPL 不能直接平均（困难｜计算，15 分）

两个独立计分窗口，分别有 100 个有效预测 token、NLL 总和 100，以及 300 个 token、NLL 总和 600。求总体 NLL 和 PPL，并解释为什么不平均两个窗口 PPL。

<details><summary>参考答案与评分要点</summary>

**参考路径一：**

总平均 NLL 为 $(100+600)/(100+300)=1.75$，PPL 为 $e^{1.75}\approx5.75460$。两个窗口 PPL 为 $e^1$ 与 $e^2$，直接平均约 5.05367，既没有按有效 token 加权，也在指数变换后错误聚合。必须固定 shift/掩码和窗口协议。

**解法二：概率几何平均。** 各窗口平均NLL为1和2，按token加权为0.25×1+0.75×2=1.75；PPL是各窗口PPL按该权重的几何平均，而非算术平均。

**验证路径：逐token累计。** 用统一掩码逐token求−logp总和与计分数，再在最后一次exp；可检查窗口重叠是否重复计分和padding是否进入分母。

**评分要点：** 有效分母 4 分；NLL/PPL 5 分；错误聚合解释 4 分；协议 2 分。

</details>

### 10-04｜TTFT、TPOT 与 ITL（困难｜计算，15 分）

请求在 0 ms 发出，四个输出 token 分别于 120、160、220、270 ms 到达。计算 TTFT、E2E、三个 ITL 和 TPOT。如果只输出一个 token，TPOT 应怎样处理？

<details><summary>参考答案与评分要点</summary>

**参考路径一：**

TTFT=120 ms，E2E=270 ms，ITL=[40,60,50] ms，TPOT=(270−120)/(4−1)=50 ms。单 token 没有后续间隔，应标注不适用或单独声明指标约定，不能按不存在的间隔解释为零延迟。

**路径二：望远镜求和。** ITL之和为最后−首个时间=150，除3个间隔得50；这说明n个token只有n−1个后续间隔。

**路径三：时间线分解。** 请求总耗时=首token等待120+后续生成150=270。若客户端按chunk接收，chunk时间不一定能还原逐tokenITL，需说明数据采集粒度。

**评分要点：** 两个端点指标 4 分；ITL/TPOT 7 分；单token约定 4 分。

</details>

### 10-E02｜算术平均PPL会如何偏差（困难｜拓展题，单独计分）

<details><summary>参考答案与评分要点</summary>

**解法一：先取log。** 平均NLL=(ln2+ln8)/2=ln4，总体PPL4；算术平均5。

</details>

<a id="exercise-10-e03"></a>

### 10-E03｜怎样证明质量下降没有超过可接受门槛（特别困难｜拓展题，单独计分）

同一固定测试集成对比较准确率，差值d=量化−浮点。预先设可接受下限−1个百分点。试验甲差值95%区间[−0.8,0.2]个百分点，乙为[−2.0,0.2]。哪种结果支持预设非劣要求？设计两种合理统计方案，说明“不显著”为什么不等于“非劣”。

<details><summary>参考答案与评分要点</summary>

**方案一：配对bootstrap。** 按独立题目/文档单位重采样，计算差值区间；在题设有效区间下，甲整个区间高于−1，支持该门槛；乙仍含不可接受下降，证据不足。

**方案二：配对二项/差值模型。** 从两模型不一致结果构造差值推断，或预先定义分层估计再合并；需明确独立单元与区间方法。不同方法可能给不同区间，不能在看到结果后挑有利方法。

**逻辑路径：** 两区间均含0，只表明未排除无差异；非劣需要排除“差于−1”的区域。质量门槛、置信水平、重复尝试与任务范围需事先固定，不能由某个有利区间宣称所有任务无损。

**评分要点：** 单独按 10 分评价：结论与条件 3 分、推理或设计过程 5 分、独立核验与边界 2 分。评分覆盖题干要求的全部子问；未要求比较多解时，可任选或组合参考路径完成作答。数值核验不能替代题干明确要求的证明，多解数量不额外加分。

</details>

**复习建议：** 计算错误先回到本章的形状、单位与约定；工程判断缺少依据时，补写目标函数、对照配置和验证边界。建议达到 80 分后继续；这是一项自学建议，不是经教学验证的能力认证标准。
